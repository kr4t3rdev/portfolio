01 / EL PROBLEMA

Un producto no termina en el CRUD.

Un catálogo necesita productos. Una operación empresarial necesita además ubicaciones, documentos, usuarios autorizados y movimientos financieros. FinanceMDM aborda esa relación entre áreas, en lugar de tratarlas como pantallas desconectadas.

Soy Michel García Aguero. Desarrollé el proyecto de forma independiente durante aproximadamente dos años y continúo refinándolo. Todavía no lo utiliza ningún negocio: la validación comercial sigue pendiente.

Operación

Productos, existencias por ubicación, compras, ventas y facturación.

Finanzas

Modelos y servicios para monedas, cuentas y conciliación.

Administración

Empresas, membresías, permisos y capacidades por plan.

02 / SISTEMA

Una aplicación.
Responsabilidades distintas.

Next.js aloja tanto la interfaz como operaciones del backend. La organización por funcionalidades convive con servicios compartidos para autenticación, autorización y acceso a datos.

La API forma parte del proyecto Next.js. No se presenta como microservicios ni como un backend NestJS separado.

03 / FRONTEND

Hacer legible
la complejidad.

La interfaz organiza información administrativa mediante páginas, formularios, tablas y reportes. El objetivo es permitir que una persona entienda qué está operando, no solo mostrar datos.

01

Next.js y React

App Router organiza las páginas. Los componentes de servidor y cliente separan renderizado e interacción; las acciones y rutas conectan la interfaz con operaciones del backend.

02

TypeScript

Describe contratos de componentes, servicios y datos. Ayuda a detectar incompatibilidades durante el desarrollo, sin sustituir la validación de entradas en ejecución.

03

Tailwind CSS y Radix UI

Estilos y componentes de interacción para mantener patrones comunes en formularios, diálogos y navegación. La accesibilidad del producto completo requiere comprobaciones adicionales.

04

Zod

Los esquemas definen estructuras de entrada en módulos como productos y operaciones contables: qué datos acepta una operación y qué restricciones deben cumplir.

¿Por qué no listar todas las dependencias?

Una librería instalada no demuestra su uso ni una mejora medible. Este desglose prioriza responsabilidades; los ejemplos visuales y de ejecución se incorporarán cuando estén verificados.

04 / BACKEND

Datos con contexto.
Operaciones con reglas.

01

Prisma y PostgreSQL

El esquema relaciona empresas, membresías, productos, existencias, documentos y entidades financieras. Prisma expresa el acceso a ese modelo relacional desde el código del servidor.

02

JWT y sesiones persistidas

El flujo de autenticación inspeccionado verifica el token, consulta la sesión y comprueba vigencia y estado del usuario antes de resolver el contexto de empresa.

03

Contexto multiempresa

La empresa solicitada se contrasta con la membresía del usuario. Si no puede resolverse un contexto autorizado, la solicitud se rechaza. Este control es una parte del aislamiento, no una certificación de todas las rutas.

04

Permisos y planes

Los permisos determinan qué acciones puede realizar un usuario. Las capacidades del plan determinan qué funcionalidades tiene habilitadas la empresa. Son controles distintos.

05

OpenTelemetry y Prometheus

El código incluye instrumentación de trazas y métricas. Permite preparar el diagnóstico de operaciones y errores; no implica que colectores, alertas o paneles estén activos en producción.

05 / INGENIERÍA

Tres problemas
que merecen evidencia.

A / AISLAMIENTO

Una cuenta, distintos contextos.

Resolver una empresa no consiste en aceptar un identificador enviado por el cliente. El recorrido inspeccionado verifica su relación con el usuario.

Siguiente evidencia: demostrar el rechazo de acceso cruzado entre dos empresas con datos ficticios.

B / AUTORIZACIÓN

Ocultar un botón no basta.

El servidor controla permisos. En el flujo web inspeccionado, cuando se solicita validación de permisos, una ruta sin mapeo se rechaza. El API móvil dispone de controles propios por grupos.

Siguiente evidencia: comparar la misma operación con dos roles y comprobar su respuesta.

C / FINANZAS

Un número necesita significado.

Monedas, cuentas y conciliación forman parte del modelo. Explicar un reporte exige seguir el origen de sus datos y distinguir sus criterios, no limitarse a mostrar un total.

Siguiente evidencia: cálculo reproducible y recorrido de conciliación en un entorno de prueba.

06 / ESTADO REAL

Lo construido.
Lo que falta demostrar.

Evidencia de implementación

  • Estructura web y backend en Next.js.
  • Modelo relacional con Prisma.
  • Sesiones, contexto de empresa y permisos.
  • Configuración y archivos de pruebas unitarias, integración y E2E.

Validación pendiente

  • Uso por negocios y resultados comerciales.
  • Demostraciones completas con datos ficticios.
  • Cobertura y resultados actuales de la suite completa.
  • Verificación operativa de observabilidad.

Las cifras de archivos no equivalen a calidad, cobertura o escala operativa. Por eso este caso no utiliza contadores del repositorio como indicadores de éxito.

Cómo se construyó este caso de estudio

La explicación técnica se basa en una revisión del repositorio, no en una auditoría exhaustiva de seguridad o producción. La autoría, duración aproximada y ausencia de adopción comercial fueron confirmadas por el autor. No se incluyen capturas simuladas ni métricas de clientes.
